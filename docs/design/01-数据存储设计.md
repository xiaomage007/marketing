## 三、数据存储设计

### 3.1 MySQL 分库分表结构

路由配置（`application-dev.yml` 中 `mini-db-router`）：`dbCount=2`、`tbCount=4`、`routerKey=userId`、默认库 `db00`。

| 逻辑库 | 物理库 | 存放内容 |
|---|---|---|
| db00 | `marketing` | 全局配置表（不按用户路由，走默认数据源） |
| db01 | `marketing_01` | 用户数据表（按 userId 哈希分库） |
| db02 | `marketing_02` | 用户数据表（按 userId 哈希分库） |

#### 3.1.1 配置库（`marketing.sql`，db00）

| 表 | 说明 | 关键字段 / 约束 |
|---|---|---|
| `award` | 奖品元信息 | `award_id`、`award_key`（发奖策略标识，如 `user_credit_random`）、`award_config`（如 `1,100` 随机积分范围） |
| `raffle_activity` | 抽奖活动 | `activity_id`（唯一）、`begin/end_date_time`、`strategy_id`（唯一，活动↔策略 1:1）、`state`（create/open/close） |
| `raffle_activity_count` | 活动次数配置 | `activity_count_id`（唯一）、`total_count`、`day_count`、`month_count` |
| `raffle_activity_sku` | 活动 SKU（「活动+次数配置」组合成一个商品） | `sku`（唯一）、`activity_id`、`activity_count_id`、`stock_count`、`stock_count_surplus`、`product_amount`（商品金额【积分】，第 27 节新增） |
| `strategy` | 抽奖策略 | `strategy_id`、`rule_models`（逗号分隔，如 `rule_blacklist,rule_weight`，决定责任链顺序） |
| `strategy_award` | 策略下奖品配置 | 联合索引 `(strategy_id, award_id)`；`award_rate`（decimal(6,4)）、`award_count/surplus`（库存）、`rule_models`（**存规则树 ID**，如 `tree_lock_1`）、`sort` |
| `strategy_rule` | 规则配置 | `rule_type`（1=策略规则 / 2=奖品规则）、`rule_model`、`rule_value` |
| `rule_tree` | 规则树 | `tree_id`（唯一，如 `tree_lock_1`）、`tree_node_rule_key`（根节点） |
| `rule_tree_node` | 规则树节点 | `tree_id + rule_key`；`rule_value`（节点参数，如次数锁阈值 `1`、兜底奖品 `101:1,100`） |
| `rule_tree_node_line` | 规则树连线 | `rule_node_from → rule_node_to`、`rule_limit_type`（EQUAL）、`rule_limit_value`（ALLOW/TAKE_OVER） |
| `daily_behavior_rebate` | 日常行为返利配置 | `behavior_type`（sign 签到 / openai_pay 支付）、`rebate_type`（sku 活动库存充值商品 / integral 用户活动积分）、`rebate_config`（sku 值或积分值）、`state`（open/close，查询仅取 open） |

#### 3.1.2 用户库（`marketing_01.sql` / `marketing_02.sql`，db01/db02）

| 表 | 说明 | 分表 | 关键约束 |
|---|---|---|---|
| `raffle_activity_account` | 用户总账户（总/日/月额度 + 日/月镜像） | 不分表 | 唯一 `(user_id, activity_id)` |
| `raffle_activity_account_day` | 日账户 | 不分表 | 唯一 `(user_id, activity_id, day)`，`day` 格式 `yyyy-MM-dd` |
| `raffle_activity_account_month` | 月账户 | 不分表 | 唯一 `(user_id, activity_id, month)`，`month` 格式 `yyyy-MM` |
| `raffle_activity_order_000..003` | 活动额度充值单（sku 充值） | 4 张 | 唯一 `order_id`；索引 `(user_id, activity_id, state)`；`out_business_no` 业务幂等；`pay_amount`（支付金额【积分】，第 27 节新增，`credit_pay_trade` 场景落库）；`state`：wait_pay/completed |
| `user_raffle_order_000..003` | 用户参与抽奖单 | 4 张 | 唯一 `order_id`；索引 `(user_id, activity_id)`；`order_state`：create/used/cancel |
| `user_award_record_000..003` | 用户中奖记录 | 4 张 | 唯一 `order_id`（幂等键）；`award_state`：create/complete/fail |
| `user_behavior_rebate_order_000..003` | 用户行为返利流水订单 | 4 张 | 唯一 `order_id`；**唯一 `biz_id`（行为幂等键，`user_id_rebate_type_out_business_no` 拼接）**；索引 `user_id`；`rebate_type`：sku/integral |
| `user_credit_order_000..003` | 用户积分流水单（**第 26 节新增**） | 4 张 | 唯一 `order_id`；**唯一 `out_business_no`（业务幂等键）**；索引 `user_id`；`trade_name`（REBATE/CONVERT_SKU）、`trade_type`（forward/reverse）、`trade_amount` |
| `user_credit_account` | 用户积分账户（**第 25 节新增**） | 不分表 | 发奖消费侧入账；`account_status`：`open`/`close`（`AccountStatusVO`）；当前 DDL 仅有 PK 自增，**未加 `uq_user_id` 唯一索引**（第 27 节已用 Redisson 锁 + 先查后写缓解，见 Q10） |
| `task` | MQ 任务表（消息与投递参数落库） | 不分表 | 索引 `state`；`message_id` 与 `EventMessage.id` 对齐，消费侧幂等键；`exchange`/`routing_key`/`queue` 与 `BaseEvent` 对齐 |

**账户三表模型说明**：`raffle_activity_account` 同时保存「日额度镜像（day_count_surplus）」和「月额度镜像（month_count_surplus）」。当某个用户在新的月份/日期首次参与时，月/日子账户尚不存在，需要**从总账的镜像值初始化**月/日账户，再各自扣减——这样即使日/月账户行还没建出来，也能拿到正确的初始额度。

**关键种子数据**（本文所有举例基于此）：

```
raffle_activity:  activity_id=100301「测试活动」 2024-03-09 ~ 2034-03-09  state=open  strategy_id=100006
raffle_activity_count: activity_count_id=11101  total=1  day=1  month=1
raffle_activity_sku:    sku=9011  activity_id=100301  activity_count_id=11101  stock_count=100000  surplus=99890  product_amount=1.68

strategy: 100001 rule_models='rule_blacklist,rule_weight'；100006 rule_models=NULL（纯规则树）
strategy_rule(100001):
  rule_weight    = '4000:102,103,104,105 5000:102,103,104,105,106,107 6000:102,103,104,105,106,107,108,109'
  rule_blacklist = '101:user001,user002,user003'      ← 黑名单命中发 awardId=101

strategy_award(100006)：101(0.02) 102~108(各 0.03)
  其中 106/107 rule_models='tree_lock_1'（抽奖 1 次后解锁）
       108     rule_models='tree_lock_2'（抽奖 2 次后解锁）
       101~105 rule_models='tree_luck_award'（库存+兜底）

rule_tree: tree_lock_1(root=rule_lock) / tree_lock_2(root=rule_lock) / tree_luck_award(root=rule_stock)
rule_tree_node: rule_lock(tree_lock_1, value='1')、rule_lock(tree_lock_2, value='2')、
                rule_stock(value=NULL)、rule_luck_award(value='101:1,100')
rule_tree_node_line:
  tree_lock_1/2:  rule_lock --ALLOW--> rule_stock
                  rule_lock --TAKE_OVER--> rule_luck_award

  sign → sku      rebate_config='9011'  state=open   ← 返利 sku 9011（充值 1 次抽奖额度）
  sign → integral rebate_config='10'    state=open   ← 返利 10 积分（第 26 节起 RebateMessageCustomer integral 分支入账）

  user_id='Charlie' behavior_type='sign' rebate_type='integral' rebate_config='10'
    out_business_no='20240430' biz_id='xiaofuge_integral_20240430'
```

### 3.2 Redis Key 设计（`Constants.RedisKey`）

| Key 前缀 | 类型 | 写入时机 | 用途 |
|---|---|---|---|
| `big_market_activity_key_{activityId}` | String(对象) | 活动装配 / 首次查询回填 | `ActivityEntity` 缓存（Cache-Aside） |
| `big_market_activity_count_key_{activityCountId}` | String(对象) | 活动装配 / 首次查询回填 | `ActivityCountEntity` 次数配置缓存 |
| `big_market_activity_sku_key_{sku}` | String(对象) | 预留 | SKU 缓存（当前 `queryActivitySku` 直查 DB，未启用） |
| `big_market_strategy_key_{strategyId}` | String(对象) | 首次查询回填 | `StrategyEntity` 缓存 |
| `big_market_strategy_award_list_key_{strategyId}` | String(对象) | 装配时回填 | 策略奖品列表缓存 |
| `big_market_strategy_award_key_{strategyId}_{awardId}` | String(对象) | 首次查询回填 | 单个奖品配置缓存（构建 `RaffleAwardEntity` 用） |
| `big_market_strategy_rate_range_key_{key}` | String(int) | 策略装配 | 概率查找表总区间（rateRange） |
| `big_market_strategy_rate_table_key_{key}` | Hash | 策略装配 | 概率查找表：field=随机索引，value=奖品ID，O(1) 命中 |
| `rule_tree_vo_key_{treeId}` | String(对象) | 首次查询回填 | `RuleTreeVO` 整棵树缓存 |
| `strategy_award_count_key_{strategyId}_{awardId}` | AtomicLong | 策略装配 | 奖品库存计数器（DECR 原子扣减） |
| `strategy_award_count_query_key` | Redisson 延迟队列 | 库存扣减成功后 | 奖品库存扣减事件（3s 延迟），供 `UpdateAwardStockJob` 消费 |
| `activity_sku_stock_count_key_{sku}` | AtomicLong | 活动装配 | 活动 SKU 库存计数器（DECR 原子扣减） |
| `activity_sku_count_query_key` | Redisson 延迟队列 | SKU 扣减成功后 | SKU 扣减事件（3s 延迟），供 `UpdateActivitySkuStockJob` 消费 |
| `activity_account_lock_{userId}_{activityId}` | RLock | 无支付交易下单（`doSaveNoPayOrder`） | 活动账户充值分布式锁（3 秒），串行化同一用户同一活动的账户累加 |
| `activity_account_update_lock_{userId}` | RLock | 积分到账发货（`updateOrder`） | 订单完成 + 账户充值分布式锁（3 秒） |
| `user_credit_account_lock_{userId}_{outBusinessNo}` | RLock | 积分调额（`saveUserCreditTradeOrder`） | 积分账户开户/调额分布式锁（3 秒），按「用户 + 业务单」粒度 |

> 说明：`{key}` 在权重子表场景是 `strategyId_权重档位`（如 `100001_4000:102,103,104,105`）。两个库存计数器还会派生出**分段锁 key**：`计数key_surplus值`（如 `strategy_award_count_key_100006_106_99`），用于「同一剩余值只投递一次延迟队列消息」的防重。

### 3.3 RabbitMQ 拓扑（配置驱动）

拓扑定义在 `application-dev.yml` 的 `rabbitmq.topology` 段，由 `RabbitMqConfig` + `RabbitMqTopologyProperties` 读取并构建 `Declarables`，启动时由 `RabbitAdmin` 自动 declare。当前四个队列均为**场景①：只配队列、走默认交换机**（routingKey = 队列名）：

| 逻辑 key | 队列名 | durable | 生产方 | 消费方 |
|---|---|---|---|---|
| `activity_sku_stock_zero` | `activity_sku_stock_zero` | true | `ActivityRepository.subtractionActivitySkuStock`（SKU 库存清零时） | `ActivitySkuStockZeroCustomer` |
| `send_award` | `send_award` | true | `AwardRepository.saveUserAwardRecord`（事务提交后） | `SendAwardCustomer` |
| `send_rebate` | `send_rebate` | true | `BehaviorRebateRepository.saveUserRebateRecord`（事务提交后） | `RebateMessageCustomer` |
| `credit_adjust_success` | `credit_adjust_success`（**第 27 节新增**） | true | `CreditRepository.saveUserCreditTradeOrder`（事务提交后） | `CreditAdjustSuccessCustomer` |

消息体统一为 `BaseEvent.EventMessage<T>` JSON：

```json
{ "id": "88012345678", "timestamp": "2026-08-23 16:30:05", "data": { ... } }
```

消费侧配置：`acknowledge-mode=auto`（方法正常返回即 ack，抛异常走拒绝），本地重试 `max-attempts=3`，`prefetch=10`。
